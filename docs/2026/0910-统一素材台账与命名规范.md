# 统一素材台账与命名规范

> 日期：2026-09-10
> 状态：定稿（决策项已确认，待实施）
> 范围：MiniMovie 项目集 —— game-storyline-pipeline 及其全部子 skill（dialogue-crawler / video-crawler / bgm-crawler / intro-maker / mini-movie-maker）
> 关系：本文取代 `mini-movie-skills/docs/2026/0817-v1.0.0-物料规范.md` 中「素材管理」部分，并废除 `game-materials/genshin/plan.csv`、`mini-movie-skills/catalog.yaml` 两个文件。

---

## 1. 背景与问题

当前素材管理存在「两本账 + 软链当胶水」的结构性缺陷：

1. **两本账**：管道侧有 `game-materials/genshin/plan.csv` 和一套目录约定；mmm 侧有 `catalog.yaml` + `pipeline.sqlite` 和另一套目录约定。两者之间没有引用关系，只靠人工对齐。
2. **软链对齐**：`materials/{video_id}/source.mp4` 是软链，指向管道下载的实录文件。软链是绝对路径，跨机器迁移即失效，且「对齐」的职责压在软链上。
3. **命名扛对齐**：因为没有主键引用，`video_id` / `task_id` 必须靠字符串可读性来对齐两端，于是命名承载了本不该承载的职责——一旦分层不明确（缺「任务线」层级）、或规则缺失（task_id 无规范），就出现 `gs-16-mjzd`、`hd-16-all` 这类靠拼音缩写续命的特例。
4. **冗余**：`catalog.yaml` 与 SQLite catalog 表逐字段重复，方向又是单向（导入即覆盖），日常 `mmm add` 直写 SQLite 后 YAML 即过期，却仍被当作台账之一。

**核心结论**：把两本账合成一本、让对齐从「靠名字」变成「靠主键引用」、软链直接消失，是本方案的目标。

---

## 2. 目标与原则

1. **单一事实源**：所有素材与任务登记进入一本 SQLite 台账（`ledger.sqlite`），读、写、检索全部对齐它。
2. **三层素材管理**：`游戏 → 版本 → 任务线（主线/世界/活动）`，素材与任务都必须归类到这一层级。
3. **主键引用替代软链**：台账记录素材的相对路径，任何环节取素材都走「台账查路径」，不再依赖软链。
4. **命名可推导、冲突靠约束**：ID 从层级自动推导，唯一性由数据库 UNIQUE 约束保证，不靠人自觉。
5. **零兼容负担**：本机全部为测试数据、项目未上线，本方案只定义目标态，不对历史数据做兼容迁移。

## 3. 统一台账（核心）

### 3.1 数据库选型：SQLite

| 维度 | 结论 |
|------|------|
| 选型 | **SQLite**（不是 MySQL） |
| 理由 | 单人单写、零运维、单文件可拷（合并=拷一个文件）、现有 mmm 代码全线假设 SQLite |
| 弃 MySQL 的理由 | 并发多写 / 远端访问 / web 后台，当前一项都用不上；真要后台，SQLite 上套只读界面即可 |
| 前瞻约束 | schema 按「可移植到 MySQL」编写：主键用整型 `id`、`REFERENCES` 显式外键、不使用 SQLite 特有 hack；将来多人协作再迁移，成本为一张表结构 |

### 3.2 实体模型

```
game（游戏）
 └─ version（版本）
     ├─ quest（任务线：主线/世界/活动）
     │   └─ asset（video 分P / dialog 台词）
     ├─ asset（version 级物料：bgm / cover / intro）
     └─ task（mmm 成片任务，认领 quest）
```

区分「版本级」与「任务线级」物料：

| 素材 kind | 归属 | 说明 |
|-----------|------|------|
| `video` | quest | 实录 mp4，一个 quest 一段剧情，可多分P |
| `dialog` | quest | 台词 JSONL，一个 quest 一份 |
| `bgm` | version | 版本 BGM，不属于某条任务线 |
| `cover` | version | 版本封面成品（intro-maker 产） |
| `outro` | version | 版本片尾图（intro-maker 产，与 cover 同构） |
| `intro` | version | 版本片头视频（外部素材，非 intro-maker 产） |

### 3.3 Schema DDL

```sql
-- 素材台账（管道侧登记）

CREATE TABLE game (
    code TEXT PRIMARY KEY,          -- gs / zzz / mc
    name TEXT NOT NULL              -- 原神 / 绝区零 / 鸣潮
);

CREATE TABLE version (
    id         INTEGER PRIMARY KEY,
    game_code  TEXT NOT NULL REFERENCES game(code),
    no         TEXT NOT NULL,       -- 2.4 / 1.6（保留小数点，避免 16 与 1.6 歧义）
    name       TEXT,                -- 飞彩镌流年 / 盛夏！海岛？大冒险！
    UNIQUE(game_code, no)
);

CREATE TABLE quest (
    id         INTEGER PRIMARY KEY,
    version_id INTEGER NOT NULL REFERENCES version(id),
    type       TEXT NOT NULL,       -- main / world / event
    name       TEXT NOT NULL,       -- 中文名（展示用）
    slug       TEXT NOT NULL,       -- ASCII 短名（身份用，见 §5.4）
    UNIQUE(version_id, type, slug)
);

CREATE TABLE asset (
    id         INTEGER PRIMARY KEY,
    game_code  TEXT NOT NULL REFERENCES game(code),
    version_id INTEGER NOT NULL REFERENCES version(id),
    quest_id   INTEGER REFERENCES quest(id),  -- NULL = 版本级物料
    kind       TEXT NOT NULL,       -- video / dialog / bgm / cover / outro / intro
    seg_no     INTEGER,             -- video 分P序号（1 起）
    asset_key  TEXT NOT NULL UNIQUE, -- 命名规则生成的业务键（§5.2），目录名即它
    path       TEXT NOT NULL,       -- 相对 DATA_ROOT 的可移植路径
    source_url TEXT,                -- 溯源：wiki 页 / bilibili BV+p / OST 专辑
    sha256     TEXT,                -- 内容指纹（合并对账 / 去重）
    size       INTEGER,
    meta_json  TEXT,                -- 各 kind 的元数据（§7.2）
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 任务台账（mmm 侧，认领素材台账）

CREATE TABLE task (
    task_id    TEXT PRIMARY KEY,    -- 命名规则生成（§5.3）
    quest_id   INTEGER NOT NULL REFERENCES quest(id),
    mode       TEXT NOT NULL DEFAULT 'narrate',  -- narrate(A) / raw(B)
    variant    TEXT,                -- 变体后缀（-v2 等）
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE task_asset (          -- 替代原 task_map
    task_id  TEXT NOT NULL REFERENCES task(task_id),
    asset_id INTEGER NOT NULL REFERENCES asset(id),
    seq      INTEGER NOT NULL,     -- 剧情顺序（同一 quest 多分P 的先后）
    PRIMARY KEY(task_id, asset_id)
);
```

> mmm 原 `jobs`（断点续跑状态，易失）与 `footage_usage`（镜头防复用，业务事实）两张表**保留不变**，仅在 `task_map` 上把 `video_id` 字符串替换为 `asset_id` 主键引用。

### 3.4 关键设计点

- **`asset.path` 一律相对 DATA_ROOT**：台账记位置，取素材统一 `DATA_ROOT / path`，整棵树搬走仍有效，合并/迁移零重写——这是「不依赖软链」的技术落点。
- **`source_url` + `sha256` 承载溯源与身份**：回答「从什么地址、下载了什么」，`sha256` 是将来跨机合并对账的指纹。
- **`asset_key` 与 `id` 分离**：`id` 是内部主键（FK 引用），`asset_key` 是业务键（目录名、可读、UNIQUE）。

### 3.5 数据根配置（唯一全局变量）

数据根是 `ledger.sqlite` 与所有 `asset.path` 的锚点，由**唯一一个全局变量**承载：

| 项 | 决策 |
|----|------|
| 变量名 | `MINIMOVIE_DATA_ROOT`（取代 `MMM_DATA_ROOT`，去 mmm 前缀——它是 6 个 skill 共享的工作区根，非 mmm 专属） |
| 唯一来源 | `~/.minimovie` 文件（跨项目、与任何 skill 仓库解耦）；mmm 的 `.env` 不再持有该变量 |
| 回退链 | 进程 env（临时覆盖）> `~/.minimovie` > 默认值 |

所有子 skill 统一从这一处读数据根，消除「`.env` 与 `~/.minimovie` 两处配置」的漂移。

## 4. 目录树规范

```
DATA_ROOT/
├── ledger.sqlite                       # 统一台账（唯一事实源）
├── _sources/                           # 源素材池（不登记台账，见 §7）
│   └── {game}/posters/                 # 官方海报底图（用户自备，使用时指定）
├── {game}/                             # 游戏 code 一级
│   └── {version}/                      # 版本号（2.4 / 1.6）
│       ├── main/                       # 任务线类型：main / world / event
│       │   └── {quest_slug}/           # 任务名 slug
│       │       ├── video/p{NNN}.mp4            # 实录分P
│       │       ├── dialog/{quest_slug}.jsonl   # 台词
│       │       └── summary.md                  # 发布简介（不登记台账）
│       ├── world/
│       ├── event/
│       └── _version/                   # 版本级物料（不属于任何任务线）
│           ├── bgm/*.mp3
│           ├── cover/cover.jpg + outro.jpg
│           └── intro/intro.mov
├── workspace/{asset_key}/              # mmm 中间产物（video 级，可重建）
├── tasks/{task_id}/                    # mmm 任务产物
└── output/{task_id}/                   # mmm 成片
```

- 原 `materials/` 目录与 `materials/{video_id}/source.mp4` 软链**整体删除**，mmm 从台账 `asset.path` 取素材。
- 各采集器不再自建 `dialogs/{版本}/`、`video-recording/{版本-系列}/`、`musics/{版本}/` 等异构目录，统一落本树并写台账。

## 5. 命名规范

### 5.1 层级枚举

| 层级 | 取值 | 示例 |
|------|------|------|
| game code | 游戏缩写 | `gs`（原神）/ `zzz` / `mc` |
| version no | 版本号，保留小数点 | `2.4` / `1.6` |
| quest type | `main` / `world` / `event` | 主线 / 世界 / 活动 |
| quest slug | ASCII 短名（§5.4） | `feicai-liunian` / `midadao` |

### 5.2 asset_key（即 mmm 的 video 处理单元标识）

```
{game}-{version}-{type}-{quest_slug}-p{NNN}     # video 分P
gs-2.4-event-midadao-p001
```

其余 kind 的 `asset_key`：

| kind | asset_key 形态 |
|------|----------------|
| dialog | `{game}-{version}-{type}-{quest_slug}` |
| bgm | `{game}-{version}-bgm-{序号}` |
| cover | `{game}-{version}-cover` |
| outro | `{game}-{version}-outro` |
| intro | `{game}-{version}-intro` |

### 5.3 task_id

```
{game}-{version}-{type}-{quest_slug}[-{mode}][-{variant}]
gs-2.4-event-midadao          # A 模式成片
gs-2.4-event-midadao-b        # 同素材 B 模式快照
gs-2.4-event-midadao-v2       # 重剪变体
```

- `-b` / `-v2` 等后缀在 `task.variant` 字段可查，不靠人记；「先 A 后 B」的两任务由相同前缀天然配对。

### 5.4 quest_slug（已定）

采用 **ASCII 短名**：登记时自动建议拼音缩写、人确认后固化，`UNIQUE(version, type, slug)` 兜底。作为 ID/SQL 键/目录名零编码问题、跨平台稳；中文名保留在 `quest.name` 展示，不参与路径身份。

## 6. 登记与认领流程

### 6.1 管道模式（默认）

```
阶段1 台词   dialogue-crawler → 落 dialog 目录 → 登记 ledger(asset, kind=dialog)
阶段2 视频   video-crawler    → 落 video 目录  → 登记 ledger(asset, kind=video)
BGM/封面     bgm/intro-maker  → 落 _version/   → 登记 ledger(asset, kind=bgm/cover/intro)
                ↓ 每阶段闸口0：确认 game/version/type/quest_slug
阶段3 浓缩   mmm task-create --claim {quest_slug}
                ↓ 从 ledger 查该 quest 的 video+dialog 资产路径，写 task_asset
             mmm run ... → 成片
```

### 6.2 独立模式（mmm 单独跑，无管道）

```
mmm add-asset …（反向注册：把本地素材登记进同一本 ledger）
mmm task-create --claim {quest_slug}
mmm run ...
```

两种模式**共用同一本 ledger**，区别仅在「谁执行登记」；登记实现只有一份，不产生第二套台账。

### 6.3 登记契约（每登记一个 asset 必写）

```
(game_code, version_id, quest_id?, kind, seg_no?, asset_key, path, source_url, sha256, meta_json)
```

检索统一走 SQL：`mmm find` / `mmm locate` 直接顶用，不再翻目录。

## 7. 各环节契约（物料规范 v2）

契约分两层，均写入 `mini-movie-skills/docs/2026/0817-v1.0.0-物料规范.md` 的 v2 修订。

### 7.1 文件层契约

| kind | 文件 | 格式 | 说明 |
|------|------|------|------|
| dialog | `dialog/{slug}.jsonl` | JSONL，UTF-8 无 BOM | 沿用现有 output-spec：`text/speaker/voiced`；伴生 `.meta.json` 取消，`sections`/`characters`/`source_url` 进 ledger |
| video | `video/p{NNN}.mp4` | mp4(h264) | `seg_no` 为 quest 内剧情序号（登记时确认），非 bilibili 分P号；伴生 `.meta.json` 取消，meta 进 ledger |
| bgm | `_version/bgm/*.mp3` | mp3 | 版本 OST 轻柔候选 |
| cover | `_version/cover/cover.jpg` | jpg 1920×1080 | intro-maker 封面成品 |
| outro | `_version/cover/outro.jpg` | jpg 1920×1080 | intro-maker 片尾成品，与 cover 同构 |
| intro | `_version/intro/intro.mov` | mov/mp4 | 片头视频，外部素材（intro-maker 不产，只登记） |

**不登记台账的两类**：

| 项 | 位置 | 说明 |
|----|------|------|
| 底图（官方海报） | `_sources/{game}/posters/` | 纯外部资源，用户自备；生成封面时显式指定/确认路径，可来回换图试效果 |
| Markdown 简介 | `{quest_slug}/summary.md` | 发布时参考，用于填视频标题与介绍 |

### 7.2 记录层契约（ledger 的 `meta_json` 字段）

| kind | meta_json 关键字段 |
|------|-------------------|
| video | `source_url`(bilibili BV+p) / `bvid` / `page`(原始分P号) / `page_title` / `duration_sec` / `resolution` / `size` |
| dialog | `source_url`(wiki 页) / `sections` / `characters` |
| bgm | `source_url`(OST 专辑) / `bpm` / `rms` |
| cover | `source_url`(官方海报) / `bg` 素材源 |
| outro | 同 cover |

## 9. 决策记录（ADR 候选）

1. **SQLite 而非 MySQL**：单人单写 + 零运维 + 单文件可拷，schema 按可移植写。可逆（将来迁移成本低）。
2. **主键引用替代软链**：台账记相对路径，跨机迁移零重写。软链是绝对路径脆弱的根源。
3. **quest 层独立成表**：`type` 枚举 + `slug` 唯一约束，替代「把主线/活动塞进文件名」的旧法。
4. **数据根单变量化**：改名 `MINIMOVIE_DATA_ROOT` + 收敛 `~/.minimovie` 唯一来源，消除数据根两处配置（§3.5）。
5. **references 文档去冗余**：`stage-*.md` 不复制子 skill 内容，只保留编排层独有逻辑（闸口0 等），子 skill 用法引用各自 SKILL.md。
6. **asset_id 单一标识**：持久化数据只存 asset_id，asset_key 仅做目录/CLI 稳定锚点；智能体操作，不为人可读性做冗余。

## 12. mmm 本体改造

> 操作者前提：Skills 由智能体读取并代为操作，设计不为人可读性做冗余。

### 12.1 身份标识：asset_id 单一标识

| 层 | 存什么 |
|----|--------|
| 台账 `asset` 表 | `asset_id` + `asset_key` + `path`（完整信息，台账职责） |
| EDL / task.json / footage_usage / keep_requirements | 只存 `asset_id`（引用，无副本） |
| 目录名 | `workspace/{asset_key}/` |
| CLI 参数 | `mmm run shots {asset_key}` |

- `asset_key` 保留目录名 + CLI 两个操作接口用途，理由不是可读性，而是**跨数据重建稳定**：`asset_id`（auto-increment）重建会重分配，`asset_key`（命名规则生成）重建不变，断点续跑不因 id 漂移失联。
- 智能体查台账 `asset_id → asset_key → path` 一次拿全，派生数据不带 asset_key 副本。

### 12.2 video_id 消费点（11 处 → asset）

| 消费点 | 现状 | 目标 |
|--------|------|------|
| 视频定位 | `materials/{video_id}/source.mp4`（cli.py / stage_asr.py 共 6 处） | `resolve_video(asset_key)` 查 `asset.path` |
| 台词定位 | `task.json script_path` / `catalog script_path` | `resolve_dialog(quest_id)` 查 `asset.path` |
| workspace | `workspace/{video_id}/` | `workspace/{asset_key}/` |
| catalog | `catalog.video_id` 主键 | 删，并入 `asset` |
| task_map | `(task_id, video_id)` | `task_asset(task_id, asset_id, seq)` |
| footage_usage | `(video_id, shot_id)` | `(asset_id, shot_id)` |
| jobs key | `video_id` 塞进 `task_id` 字段 | 字段改名 `key`：`asset_key` / `task_id` / `{task_id}:{asset_key}` |
| EDL / task.json / keep_requirements | `video_id` | `asset_id` |
| 锁 key | `video:{video_id}` | `video:{asset_key}` |
| CLI 参数 | `shots/vision/align {video_id}` | `shots/vision/align {asset_key}` |

### 12.5 版本级物料引用

task 认领 quest 时，正片素材（video+dialog）写 `task_asset`；版本级装饰物料（bgm/cover/outro/intro）在 `task.json` 以 asset_id 引用：

```json
{"composition": [{"type": "cover", "asset_id": 30}, {"type": "outro", "asset_id": 31}],
 "bgm_playlist": [{"asset_id": 20}, {"asset_id": 21}]}
```

- 校验：无 video → 报错；无 dialog → A 模式报错、B 模式放行。
- 冒烟测试入口（`--path`）跳过台账，`workspace/_smoke/` 原样不动。

### 12.6 series → game

`series` 概念映射为 `game`（游戏）。类型适配层 `config/series/{系列}.yaml` → `config/game/{game}.yaml`；TTS 词库 `config/tts/{系列}.yaml` → `config/tts/{game}.yaml`。
